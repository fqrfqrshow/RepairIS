# Ретроспектива Практической работы №3

## Что получилось

1. Настроена модель ветвления с единственной долгосрочной веткой main.
2. Настроена защита ветки main через Branch Protection Rules.
3. Созданы 4 задачи в трекере (Issues #13–16).
4. Созданы 4 ветки под задачи с говорящими именами.
5. Все коммиты оформлены по Conventional Commits с ID задачи.
6. Смоделирован конфликт слияния в README.md между двумя ветками.
7. Созданы и слиты 4 Pull Request.
8. Разрешён конфликт слияния.
9. Оформлен CHANGELOG.md в формате Keep a Changelog.
10. Создан аннотированный тег v0.1.0 и страница релиза.

## Трудности

1. Проект выполнялся одним участником — для слияния PR временно снималось требование approve.
2. Ревью проводилось самостоятельно — комментарии оставлялись к собственным PR.
3. Конфликт слияния возник в первой строке README.md — разрешён выбором варианта из main.
4. Защита ветки main мешала прямым коммитам — приходилось использовать PR даже для мелких изменений.

## Выводы

1. В дальнейшем использовать отдельные ветки под каждую задачу.
2. Всегда оформлять коммиты по Conventional Commits.
3. При работе в команде обязательно проводить взаимное ревью.
4. Разрешать конфликты сразу после их возникновения.
5. Вести CHANGELOG.md с первого релиза.
6. Использовать семантическое версионирование (SemVer).

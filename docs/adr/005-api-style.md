# ADR 005. Выбор стиля взаимодействия API

## Контекст
Проект RepairIS (ИС ремонтного предприятия) реализуется как desktop-приложение (C#, Windows Forms) с файловым JSON-хранилищем. Требуется контрактный интерфейс для интеграции с внешними потребителями (мобильный клиент, платёжный шлюз, система уведомлений) и для тестирования без доступа к коду.

## Решение
Базовый стиль — REST поверх HTTPS, формат JSON, спецификация OpenAPI 3.0.
Причины:
- простота и предсказуемость для потребителей;
- документируется Swagger UI / Redoc;
- легко тестируется curl/Postman/Bruno;
- согласуется с ролевой моделью (заказчик / менеджер / мастер).

Рассматривались как направления развития:
- WebSocket — real-time уведомления о смене статуса заявки и назначении мастера;
- Очередь сообщений (RabbitMQ/Kafka) — событийная интеграция.

Не выбраны как базовые: SOAP, GraphQL, gRPC.

## Последствия
- Контракт фиксируется в docs/api/openapi.yaml до реализации (API-first).
- Любое изменение контракта — сначала в спецификации, затем в коде, с записью в docs/api/changelog.md.
- Появляется единый слой интеграции для всех клиентов.

# ADR-002. Выбор инструмента миграций

## Статус
Принято.

## Контекст
Проект RepairIS использует JSON-хранилище (файлы orders.json, users.json и др.). По мере развития системы структура данных может меняться: добавляются новые поля, меняются типы, появляются новые сущности.

Необходимо:
1. Отслеживать историю изменений структуры.
2. Применять изменения воспроизводимо на любой копии данных (машина разработчика, тестовый стенд, production).
3. Избежать «дрейфа схемы» — ситуации, когда структуры данных в разных окружениях расходятся.

Возможные варианты:
1. **Ручные миграции** — разработчик вручную редактирует JSON-файлы.
2. **Скрипты на C#** — методы `MigrateXXX()` в адаптерах.
3. **Файловые миграции** — отдельные JSON/текстовые файлы с описанием изменений.
4. **Внешний инструмент** — Flyway или Liquibase (изначально для SQL).

## Решение
Выбран **вариант 2 + 3**: скрипты на C# + файловые миграции.

Реализация:
1. Создана папка `migrations/` в корне проекта.
2. Каждая миграция — отдельный файл (`001_create_tables.md`, `002_add_priority.md` и т.д.).
3. В коде приложения реализованы методы-миграции (`MigrateAddPriority()` в `OrderAdapter`), которые запускаются при старте.
4. Версия применённых миграций хранится в файле `migrations_applied.json`.

## Последствия

**Положительные:**
1. Простота — не требует установки внешних инструментов.
2. Прозрачность — история миграций хранится в репозитории.
3. Воспроизводимость — при запуске приложения миграции применяются автоматически.
4. Совместимость с Git — миграции версионируются вместе с кодом.

**Отрицательные:**
1. Нет автоматической генерации миграций (как в Alembic или Django).
2. Нет встроенной поддержки отката (rollback) — нужно реализовывать вручную.
3. При больших объёмах данных миграция может занимать много времени.

## Альтернативы
1. **Flyway / Liquibase** — отклонены, так как ориентированы на SQL-СУБД, а не на JSON.
2. **Ручные миграции** — отклонены из-за высокого риска ошибок и «дрейфа схемы».

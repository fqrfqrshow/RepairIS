# Модель ветвления проекта RepairIS

## Выбранная модель

Для проекта выбрана упрощённая Flow-модель с единственной долгосрочной веткой main.

## Основные принципы

1. Ветка main — единственная долгосрочная ветка. Она всегда содержит рабочую версию проекта.
2. Все изменения вносятся через временные ветки, которые создаются под конкретные задачи.
3. После завершения работы ветка вливается в main через Pull Request.
4. Прямые коммиты в main запрещены (настроена защита ветки).

## Правила именования веток

Формат имени ветки:

```
<тип>/<id-задачи>-<краткое-описание>
```

Типы веток:

1. feature/ — новая функциональность
2. docs/ — документация
3. fix/ — исправление ошибок
4. chore/ — технические изменения
5. refactor/ — рефакторинг

Примеры:

1. docs/13-branching-model
2. feature/15-health-check
3. fix/17-readme-typo

## Правила коммитов (Conventional Commits)

Формат сообщения коммита:

```
<тип>(#<id-задачи>): <краткое описание>
```

Типы коммитов:

1. feat — новая функциональность
2. fix — исправление ошибки
3. docs — документация
4. chore — технические изменения
5. refactor — рефакторинг

Примеры:

1. docs(#13): add branching model description
2. feat(#15): add health-check
3. fix(#17): fix typo in README

## Защита основной ветки

Для ветки main настроены правила:

1. Запрещены прямые коммиты.
2. Требуется минимум 1 одобрение через Pull Request.
3. Обязательное прохождение автоматических проверок (при наличии).

## Процесс работы

1. Создать Issue с описанием задачи.
2. Создать ветку от main с именем по формату.
3. Работать в ветке, коммитить по Conventional Commits.
4. Запушить ветку в GitHub.
5. Создать Pull Request в main.
6. Провести ревью, внести правки.
7. Выполнить merge после одобрения.
8. Удалить временную ветку.

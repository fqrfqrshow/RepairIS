# Обеспечение согласованности и транзакционности при работе с JSON

## 1. Проблема транзакций в файлах
В отличие от СУБД, JSON-файлы не поддерживают транзакции `BEGIN` / `COMMIT` / `ROLLBACK` из коробки. Если при записи файла произойдёт сбой (отключение питания), файл может быть повреждён.

## 2. Как реализован принцип «всё или ничего» (Atomicity)
В классе `OrderAdapter` при сохранении заявки используется паттерн **безопасной записи**:
1. Сериализованные данные записываются во временный файл `orders.tmp.json`.
2. Выполняется проверка: файл успешно записан.
3. Временный файл переименовывается в `orders.json` (переименование на уровне файловой системы атомарно).
4. При ошибке временный файл удаляется, а основной `orders.json` остаётся нетронутым.

**Таким образом, мы имитируем транзакцию: либо данные записаны полностью, либо не записаны вообще.**

## 3. Демонстрация: отказ при ошибке (аналог ROLLBACK)
**Сценарий:** Попытка сохранить заявку с некорректными данными (например, `clientId = null`).
1. Приложение выбрасывает исключение `ArgumentNullException`.
2. Запись в `orders.tmp.json` прерывается.
3. Исходный `orders.json` не изменяется.
*Результат: база вернулась в исходное состояние.*

## 4. Уровни изоляции
В файловой системе нет уровней изоляции, так как доступ к файлам обычно происходит в одном потоке (в Windows Forms). Для предотвращения одновременного доступа используется блокировка файла (FileStream с `FileShare.Read`).
